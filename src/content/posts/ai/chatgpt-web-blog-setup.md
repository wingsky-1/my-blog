最近一直在折腾 VPS、家庭组网、Docker，还有 Codex 和各种 AI Agent。

折腾的东西越来越多，遇到的问题也不少。很多方案当时研究得挺深入，过段时间想再找出来，还得去翻聊天记录。总这样也不是回事。

所以就想着，干脆搭个自己的技术博客，把这些实践整理一下。以后查起来方便，有些方案也可以直接分享给别人。

本来打算选好主题，再交给本地 Codex 去实施。不过这次突然有个想法：

**既然 ChatGPT 网页版已经能连接 GitHub、Cloudflare，那我是不是可以直接在聊天窗口里把整个博客搭起来？**

说干就干。最后还真给跑通了。

从项目初始化、中文适配、安全 CI、依赖漏洞修复，到 Cloudflare Pages 部署、自定义域名绑定，基本都是直接在 ChatGPT 的对话里完成的。当然，中间也没少踩坑。

这篇就记录一下整个过程，以及我对这种 AI 工作方式的一些实际感受。

## 一、一个博客而已，为什么还要纠结选型？

其实我对博客的要求并不复杂。能写 Markdown、代码高亮好用、支持中文、最好有全文搜索，后面维护起来别太折腾就行。

但真开始选型，发现可选的东西还挺多：[Hugo](https://gohugo.io/)、Hexo、[Astro](https://astro.build/)，以及 Halo、Ghost、WordPress……

动态 CMS 确实方便，后台、编辑器、插件都比较完善。不过我平时本来就在用 GitHub 和 Markdown，后续写文章大概率也会让 Codex 帮忙整理、修改。

再为了一个个人博客维护数据库、容器和后台服务，好像没什么必要。况且家里有服务器，不代表所有东西都必须部署在家里。

**能用静态站点解决的问题，就别给自己增加运维负担了。**

最后选择了 Astro：Markdown/MDX 支持完善、TypeScript 生态熟悉、扩展空间足够，而且静态构建比较适合我的场景。

**主题反而纠结得更久**

最开始比较关注 Fuwari、AstroPaper、Pure、Mizuki，后面又看了 Cactus、AstroWind。

有些确实好看，功能也丰富。但我比较在意 GitHub 上的维护情况，尤其是 Issue 和 PR。毕竟博客准备长期用，不能只看截图好不好看。

最终选了 [AstroPaper](https://github.com/satnaing/astro-paper)。

它不算特别花哨，但 Markdown/MDX、标签、RSS、SEO、明暗主题、全文搜索基本都有，整体结构比较清晰。

不过 AstroPaper 更像一个能直接修改源码的项目模板，并不是安装后完全不用碰代码的主题插件。这意味着自定义很方便，同步上游时也得注意冲突。

> 能通过配置解决，就不要为了一个小功能大改源码。

## 二、有 VPS、有家庭服务器，为什么还是选 Cloudflare？

最开始也考虑过 Docker + Caddy。不过仔细想想，一个基本只有静态页面的技术博客，确实没必要占用自己的服务器资源。

最终决定用 GitHub 管理文章，[Cloudflare Pages](https://pages.cloudflare.com/) 负责构建和发布。

```text
ChatGPT 网页版
    ├── GitHub
    │   ├── 文章和代码
    │   ├── Pull Request
    │   └── Actions / 安全检查
    └── Cloudflare
        ├── Pages
        ├── DNS
        └── HTTPS
              ↓
          个人技术博客
```

这里顺便说个经常被问到的问题：**Cloudflare Pages 和 Workers 到底选哪个？**

只是 AstroPaper 静态博客，Pages 就够了。没有服务端逻辑，也不需要额外创建 Worker。以后真有动态接口，再考虑也不迟。

**那国内访问怎么样？**

看到这里，可能有人已经想问了：_Cloudflare 在国内的访问体验，不是一直有点一言难尽吗？_

确实。不同地区、运营商和网络环境下，访问表现可能有明显差异。

不过对于目前这个主要记录个人技术实践的博客，我还是更看重低维护成本和部署便利性。

而且，既然你已经成功访问到这里，还对技术博客、Cloudflare 和 AI 感兴趣，那这个问题应该也难不倒你。

当然，这不代表访问体验不重要。后续如果国内读者多了，还是得根据真实访问情况再优化。

**域名也交给 Cloudflare 管理**

域名本来就在 Cloudflare 上，所以自定义域名绑定相对简单。

不过 Cloudflare 管理域名、注册域名、DNS 托管，以及国内访问和备案，其实是几个不同的问题。

**这部分准备之后单独写一篇，聊聊为什么选择 Cloudflare 管理域名，以及在国内使用需要注意什么。**

先继续折腾博客。

## 三、这次重点来了：直接让 GPT 操作 GitHub

选型讨论完，我直接问了一句：

> 那你能先帮我创建 GitHub 项目并发布到 CF 吗？

以前 GPT 大概率会给我一套命令，告诉我怎么 clone、配置、部署，再让我自己执行。

但这次连接 GitHub 和 Cloudflare 后，GPT 能直接读取仓库、修改文件、创建分支、提交 PR，还能查看 Actions 日志和操作部分 Cloudflare 资源。

**第一个问题：居然没法直接创建仓库**

开局就遇到了限制。虽然 GitHub 已连接，但当时可用的操作里没有新建仓库。

所以我自己使用 AstroPaper 官方模板创建了仓库 `wingsky-1/my-blog`，然后把链接发给 GPT。

**连接了某个服务，不代表 AI 天然拥有它的全部操作权限。** 具体能做什么，还是看授权和接口能力。

后面它开始修改配置、添加中文、创建安全 CI、创建 Pages 项目、提交 PR。

整个过程我基本没打开本地编辑器。看着聊天窗口里的操作记录，再去 GitHub 看真实提交，确实和以前让 AI 生成代码的体验不太一样。

但问题也很快来了。

## 四、第一次 CI 就翻车

中文化时，GPT 添加了 `zh-CN` 语言文件，却没有同步修改 Astro 的 i18n 路由配置。

结果一构建，直接报错：

```text
MissingLocaleError:
The locale/path zh-CN does not exist
in the configured i18n.locales
```

后面 GPT 读取构建日志，定位到 `astro.config.ts`，补齐配置后再提交。

这只是第一个问题，后面还遇到了 Prettier 检查失败、依赖安全漏洞、Shiki 类型冲突、示例内容清理不完整……

一开始确实有点烦，但这恰好也是整个流程比较有价值的地方。

以前碰到问题，需要我把日志复制给 AI。现在它可以直接读 Actions 日志，再继续修改 PR。

> CI 能帮忙发现问题，但前提是你真的配置了检查，而且没有为了让它通过就把检查关掉。

## 五、安全 CI，比搭博客本身还折腾

一开始就强调：**记得做安全相关的 CI。**

后面会频繁用 Codex 和其他 Agent 维护。既然有不少代码并不是自己逐行写的，至少得有自动化检查兜底。

| 检查                | 用途                    |
| ------------------- | ----------------------- |
| ESLint / Prettier   | 代码规范和格式          |
| Astro Check / Build | 类型与构建              |
| Gitleaks            | 检测误提交的密钥、Token |
| pnpm audit          | 扫描依赖漏洞            |
| GitHub Ruleset      | 保护主分支              |
| Dependabot          | 跟踪依赖安全和版本更新  |

其中 Ruleset 还是我自己在网页上配置的，GPT 当时没有相应操作权限。

**新项目居然扫出几十条漏洞？**

第一次看到 `pnpm audit` 结果时，确实挺意外。

后来发现不少是传递依赖；而且要区分构建依赖和线上运行时的实际风险。静态网站不代表这些问题都能被公网利用，但也不能因此全部忽略。

于是 GPT 开始调整版本、更新锁文件。修着修着，又遇到 Shiki 类型版本不兼容。

很有平时折腾 Node.js 项目的感觉了。

后面还单独处理了 `postcss-selector-parser`：明明已经存在修复后的 7.x，锁文件里居然还保留了受影响的 6.x。

**看到某个包已经升级，不代表整个依赖树里都没有旧版本。**

最后通过重新解析锁文件、CI 构建和安全扫描才完成修复。不过这种强制升级也有兼容性风险，不能无脑上最新版。

## 六、然后 GitHub 被机器人 PR 刷屏了

安全检查搭起来后，又发现仓库里一下多了很多 Dependabot PR。

我当时还问 GPT：

> 这些都是有意义的吗？还是只要不是最新都会提交 PR？

答案是后者也占了不少。

Dependabot 除了安全修复，也会按计划检查普通版本。哪怕只是一个不涉及漏洞的 patch 更新，也可能单独提 PR。

总不能每天打开 GitHub，第一件事就是给十几个机器人 PR 点合并吧？

所以后来调整了策略：安全更新优先，普通版本降低频率，minor/patch 分组，major 版本单独评估。

之前积累的 PR 也逐个核对。已被主分支覆盖的关掉，有必要的更新通过 CI 后再合并。

**自动化不是越多越好，关键是别让自动化本身变成新的维护负担。**

## 七、以为上线了，首页还是原作者的内容

这一段有点好笑。

前面中文配置、CI、安全扫描、部署都完成了，打开博客发现还有一堆主题作者的演示文章。

于是又让 GPT 全量清理：文章、图片、About、README、赞助信息……

重新构建、检查、部署，一切正常。

这次应该没问题了吧？

结果首页迎面就是一句：

**Mingalaba**

下面还是 AstroPaper 的英文介绍。

……

原来首页文案直接写在 `src/pages/index.astro` 中。删掉 Markdown 文章，自然影响不到它。

只好再提 PR，修改首页、重新部署。

**代码检查全通过，不代表最终页面就符合需求。**

特别是「把整个模板初始化干净」这种范围有点模糊的任务，AI 很容易漏掉某个组件。

总不能上线之后，还在给原作者打广告。

## 八、终于把自己的域名绑定上了

Pages 会提供一个 `pages.dev` 地址，但既然是个人博客，肯定还是想用自己的域名。

最后选了 `blog.唐意.top`，根域名留着以后用。

GPT 直接调用 Cloudflare 接口添加自定义域名，创建 CNAME，等待域名验证和 HTTPS 证书生效。

中间还提示缺少 CNAME，补齐后才完成验证。

另外还得修改 AstroPaper 的 `site.url`。否则网站虽然能打开，RSS、Sitemap、Canonical 及分享链接却可能继续指向旧域名。

这些细节不复杂，但确实容易忽略。

最终 GitHub PR 合并，Cloudflare 自动构建，网站正式使用自己的域名。

## 九、中文博客还要考虑搜索、分类和分享图片

网站能打开，还不代表彻底收工。

**搜索：暂时不引入新服务**

AstroPaper 已集成 [Pagefind](https://pagefind.app/)，构建阶段扫描静态 HTML 生成索引，浏览器负责检索。

对于 Docker、Linux、Headscale、Cloudflare 这些技术术语，关键词搜索基本符合需求。

但它不是 AI 语义搜索。

例如你搜「怎么在外面访问家里的 NAS」，文章只写了「Tailscale 子网路由」，搜索未必能理解二者的关系。

目前博客文章还不多，就没必要上来搭一套搜索后端或向量数据库。等内容多起来，真实测试过召回率再说。

**分类和标签：先别魔改**

采用「目录管理内容、标签负责导航」：

```text
src/content/posts/
├── vps/
├── linux/
├── network/
├── ai/
└── dev/
```

写家庭组网放 `network/`；Codex、MCP、Agent 放 `ai/`。既简单，也便于后续维护。

**OG 分享图片：中文字体也得管**

文章分享到其他平台时，标题、简介和封面能否正常显示也很重要。

尤其是中文字体。为此又给 OG 图片生成加了中文字形支持。当然，真正的分享效果还要到平台里测试，不能单凭构建通过就认定没问题。

## 十、全程 GPT 网页版，到底是什么体验？

最大的变化其实不是博客部署方式，而是整个工作流程。

以前大致是：

```text
问问题 → 拿代码 → 自己执行
   ↑                 │
   └── 报错再发回来 ←┘
```

现在更接近：

```text
提出需求
   ↓
GPT 操作 GitHub / Cloudflare
   ↓
创建 Pull Request
   ↓
CI、安全扫描、Pages 预览
   ↓
GPT 读日志、修复问题
   ↓
我检查结果
   ↓
合并并发布
```

区别还挺明显。不需要反复开本地编辑器，也少了大量复制日志、粘贴命令的操作。

尤其是配置修改、PR 管理和 CI 排查，体验提升很明显。

**但它也不是完全不用管**

功能第一次没配完整，安全修复引入了依赖兼容问题，模板内容清理漏掉首页……这些全都真实发生过。

而且为了修依赖，GPT 还临时添加过带写权限的工作流，后面需要专门检查有没有清理干净。

所以我更倾向于：

**技术方向由我决定，GPT 负责执行和排查，CI 负责基础质量验证，最终效果自己验收。**

**那为什么不用 Codex？**

其实我平时也在用 Codex，也一直在研究模型、Agent 和开发工作流。

这次刻意选 GPT 网页版，就是想看不依赖本地开发环境，到底能把项目推进到什么程度。

至于 Codex 订阅怎么选、额度够不够，还有一些国内用户比较关心的订阅方式……

这又是另一个话题了。

**之后单独聊聊我自己是怎么选和使用 AI 编码工具的。**

## 十一、最后说两句

博客最后采用了 **AstroPaper + GitHub + GitHub Actions + Cloudflare Pages**。

文章用 Markdown 管理，Pagefind 搜索，Dependabot 更新依赖，CI 做代码和安全检查。

没有数据库，没有常驻后端，也不用自己维护 Web 服务器。

更重要的是，这次 GPT 网页版已经不只是一个给建议的聊天工具了。在连接 GitHub 和 Cloudflare 后，它确实能参与真实项目的实施、排错、验证和部署。

但离「发完需求就完全不用管」还有距离。

**别只看 AI 告诉你已经完成，记得去看 PR、CI、实际页面和部署结果。**

毕竟这次首页的 `Mingalaba`，都是上线后才发现的。

不过有件事还没做完：**上游主题的升级适配流程**。

现在博客是基于 AstroPaper 官方模板初始化的。后续上游更新了 Astro、MDX、页面布局或者构建方式，不能直接把新版本覆盖进来，不然中文适配、OG 图片、右侧大纲这些本地改动可能会被冲掉。

我的计划是另外整理一套升级流程：先对比上游 Release 和变更记录，再在独立分支评估差异；能同步的配置和安全修复尽量同步，涉及自己修改过的组件则逐项合并，最后经过类型检查、安全扫描、Pages 预览和实际页面验收，再考虑合入主分支。

有条件的话，后面也可以让 Codex 定期检查上游变化，但只负责生成升级建议和 PR，不直接自动合并。至于具体怎么维护模板上游，等这套流程真正跑通后，我再单独整理一篇。

写到这里，博客总算搭好了。接下来应该可以少折腾点基础设施，开始整理 VPS、家庭组网和 AI Agent 的实践了。

就是不知道，会不会写着写着又开始折腾博客本身。

希望不会。
