上次续费 ChatGPT Plus 时，我想过一个问题：每个月 20 美元，究竟是买一个更好用的聊天窗口，还是能用它搭出一套真正适合自己的工作流？

我平时用 ChatGPT 讨论技术方案，也用 Codex 改代码、审 PR。有些任务需要模型认真推敲，有些不过是查文件、整理文档、跑测试。如果所有步骤都交给同一个模型，虽然省事，但额度和能力没有用在最合适的地方。

于是我开始折腾 [Magpie](https://github.com/yetone/magpie)，把不同来源的模型接到同一个入口，让 Codex 负责组织任务，其他模型分担一部分执行工作。

这套方案有实际测通的部分，也有目前仍受 Codex 和模型服务商限制的地方。这篇记录的是我怎么想、怎么验证，以及折腾之后留下了哪些取舍，不是一份照着配置就能保证免费使用的教程。

## Plus 对我真正有价值的部分

我最常用的是 ChatGPT 里的日常讨论和工具连接。查资料、梳理架构、审查博客内容，有时直接通过 GitHub、Cloudflare 等连接完成操作。相比反复切换网页和工具，少一些操作步骤本身就有价值。

另一个是 Codex。它既能配合本地开发环境，也可以在符合资格的 Plus 账号中使用云端任务。出门时从手机查看进度、继续处理仓库里的工作，对我比单纯多聊几条消息更实用。

但这里不能把 Plus 写成「无限聊天」或者「无限远程开发」。ChatGPT 和 Codex 都有各自适用的额度、时间窗口及使用条件，云端任务也会计入相应额度。官方有时会提供一次性的额度重置，但不能当成每 28 天固定发放的长期权益。具体额度应以账号使用页面为准，参见 [OpenAI 的 Codex 套餐说明](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)。

所以我更想优化的是 **每次任务消耗在哪里**，而不是假设买了 Plus 之后就不用考虑额度。

## 我把模型分成了主控和执行两层

现在的思路比较简单：**复杂任务先由 GPT 负责拆解和验收，能明确交付标准的子任务，再按能力与额度交给其他模型。**

```text
Codex / GPT 主控
    │  拆任务、检查结果、决定是否返工
    │
    └── Magpie 统一路由
          ├── 大上下文组：较长的代码与文档任务
          ├── 常用组：日常修改、整理、检索
          ├── 免费额度组：适合批量执行的任务
          └── 付费备用组：前面几组不合适时再使用
```

Magpie 是本地运行的模型网关，能将不同账号、订阅和 API 的模型组织成路由组。对 Codex 来说，它们可以表现为统一的模型入口。它解决的是**模型接入和路由管理**，不是凭空创造免费额度，也不负责保证任务一定能跨厂商交给子代理。

分组时我更关心三件事：模型能不能完成这类任务、上下文窗口够不够，以及它实际消耗哪个账号的额度。比如一个模型标称免费，可能仅仅是不扣某一项 credits；同一账号下的其他模型仍然共享有限的资源池。

真正省下来的也不只是 token。有些重复任务让合适的模型执行，主控只关注结果，能少花不少来回检查和切换工具的时间。当然，主控调度、审查和返工本身也会消耗额度，不能简单理解为「主控几乎零成本」。

## 比起标称窗口，我更相信实际请求

接入模型以后，我没有直接照着各家宣传的上下文长度设置路由组，而是做了几轮边界测试。

**一次免费模型的上下文测试。** 当时 OpenCode Zen 的一个 DeepSeek 接口标示约 200K 上下文。我逐步增加请求大小：在那次环境里，统计约 315K 的请求通过，约 317K 的请求报了 `context_length_exceeded`。

这说明当时的接口行为与页面标称值并不完全相同，但**不能据此断言这个模型普遍拥有 315K 的稳定窗口**。请求的计数口径、系统提示、工具消息、路由后端和服务商策略都可能改变结果。我仍然给这个组配置了保守的 200K 窗口，并提前留出压缩余量，避免日常使用总在边界上试探。

**另一次是 Codex 的上下文显示。** 我曾以为经过 Magpie 后，Codex 拿不到用量信息。排查时看到相关请求返回了 `usage`，状态界面也能够显示上下文占用。对于我配置为 1M 的窗口，有效预算按 95% 计算约为 950K，压缩阈值又是另一项配置。它们不能混为一谈：**配置窗口不等于服务商实际可接受的最大请求**，有状态显示也不代表每家模型的 token 统计都绝对一致。

我现在会同时看配置、网关请求记录以及一次接近窗口的实际调用，而不是只盯着模型介绍页上的数字。

## 免费额度也要按账号算账

开始时我按 3:3:1 给三个资源池分配了路由权重，觉得小池少分一点就够了。后来才发现，如果把权重粗略当作长期请求份额，最小的一份也占了约 14%。对一个不会自动补充额度的小池来说，这个比例仍然很高。

这只是一个估算。实际调用还受上下文过滤、模型可用性、会话粘性和具体路由策略影响，不会严格按 3:3:1 扣费。但它足以提醒我：**权重首先应该保护稀缺资源，不是平均照顾每个模型。**

我也检查过 Magpie 的调用账本：当时国际版 WorkBuddy 的某个 DeepSeek 模型记录为 `credits=0`。这能证明那几次调用没有观察到对应 credits 的扣减，不能推导出整个 WorkBuddy 账号永久免费。其他模型仍可能消耗同一个账号的余额。

测试期间，我看到过部分国内服务有每日恢复额度的机制，因此优先消耗可恢复的池子，把不会恢复或需要付费的池子留作备用。但额度数值、签到规则和可用模型变化都很快，这里不把某一天看到的赠额写成读者可以长期依赖的承诺。

## 最费时间的，其实是 Codex 子代理

最初我想让第三方模型直接做主控，再派发子任务。但在当时的 Codex、模型目录和 Magpie 组合下，换成 Muse 后，预期的子代理工具没有正常出现。

我后来没有继续把「第三方模型当主控」当作这套方案的必要条件，而是选择 GPT 做主控，把其他模型放在执行层。不过这只是**我目前验证过的可用路径**，不是「所有第三方模型在所有版本的 Codex 中都绝对不能做主控」。

真正需要小心的是 Codex 多代理消息如何传递。

在 Multi-Agent V2 的部分调用路径里，主控交给子代理的任务会被后端封装为加密内容。第三方服务收到的可能不是可读的任务文本。Magpie 的兼容设置可以处理部分明文任务和模型选择问题，却无法凭空解开已经由上游加密的任务。关闭或不强制开启 V2、使用兼容的任务传递路径，有时能避开问题，但不是对任何模型组合都通用的一键修复。

我在自己的环境里做过的检查包括：固定主控与子代理模型、重开会话确认配置生效、观察子代理是否收到完整任务，以及让它返回能被主控核对的具体结果。**能启动一个子代理，不等于它确实收到了任务。**

如果准备复现，建议先阅读 [Magpie #141](https://github.com/yetone/magpie/issues/141)、[Magpie #2245](https://github.com/yetone/magpie/issues/2245) 和 [Codex #46939](https://github.com/openai/codex/issues/46939)。这些 Issue 记录了不同版本中的加密任务、跨模型兼容与明文传递诉求，不能直接把其中某个旧版本的配置当成今天的通用答案。

另一个坑是**不同窗口的模型混在一个路由组**。当请求超出某个成员能接受的范围时，它可能在路由阶段就被排除。表面上看分组里有很多模型，实际却一直由少数几个成员接单。后来我按窗口和任务类型重新分组，路由记录也更容易看懂了。

## 折腾下来，Plus 回本了吗？

如果「回本」指每个月精确省下多少 API 费用，我现在还拿不出一份严谨的对照账单：不同模型的质量、缓存命中、返工次数和服务商赠额都在变化。把 Magpie 账本里的零扣费直接换算成收益，会算得太漂亮。

但从我的使用习惯看，这笔订阅确实更值得了。ChatGPT 用来讨论和做决策，Codex 承接仓库任务，Magpie 则让我不必为了切模型反复改配置和账号。主控与执行层的分工，让我更清楚哪些环节值得用强模型，哪些地方可以试试已有的免费额度。

代价也摆在这里：要维护多个账号和路由组，要验证上下文窗口，还要处理子代理协议的版本兼容。第三方模型处理代码和文档时，也必须注意哪些内容可以发给外部服务，不能为了省额度把密钥、隐私数据和内部资料随意转发。

如果只是偶尔聊天或改个小脚本，我不会建议专门为了这套流程去买 Plus、装网关、收集免费额度。直接用一个顺手的工具更简单。

我会继续保留这套分工，但不会为了多薅一点额度继续把架构堆复杂。后续更想验证的是：**一次真实任务从拆解到验收，究竟减少了多少人工干预和返工**。这个指标，比账本上显示多少个零更能说明它有没有价值。
