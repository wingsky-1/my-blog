之前用 ChatGPT 网页版把个人技术博客搭起来以后，本以为终于可以专心写点技术笔记了。

结果第一篇文章才刚写完，又开始折腾主题。

起因其实很简单：文章一长，右侧没个目录不太方便。尤其技术文章里经常有配置和命令，想回头找某一节，只能不停往上翻。

于是加了个 TOC（Table of Contents），顺手补了字数、预计阅读时间和分享按钮。

听起来没什么难度。

结果几轮预览下来，问题反而越来越多：宽屏下正文和目录挤到一起；调整后虽然不重叠了，标题却还在原来的窄容器里，正文单独被拉宽；手机端的目录放在文章开头，读到一半想用它，还得先往回找。

本来只想加一个小功能，最后变成了重新整理文章布局。

## AstroPaper 的窄栏，真的是问题吗？

一开始看到宽屏两侧大片留白，我也想过：是不是应该把页面整体拉宽一点？

后来仔细看了 [AstroPaper](https://github.com/satnaing/astro-paper) 的源码，它本身就通过 `app-layout` 控制主要内容区域，最大宽度约 768px。Header、Footer、文章列表和普通页面都遵循这套规则。

也就是说，宽屏留白并不是主题没考虑响应式，而是一种阅读优先的选择。

想想也合理。技术文章主要还是看文字，显示器越宽，不代表一行就该塞进越多字。中文正文里又经常穿插代码、表格，太宽反而容易看得累。

真正别扭的地方，是我后来为了加右侧目录，让正文局部脱离了原来的布局体系。

之前用过类似这样的定位方式：

```css
.post-responsive-layout {
  position: relative;
  left: 50%;
  transform: translateX(-50%);
  width: min(1120px, calc(100vw - 64px));
}
```

它确实能把正文和目录拉到更宽的空间里，但标题、元信息、底部分享仍然各走各的对齐规则。

单独看每一块似乎都有道理，放在整张页面里就不协调了。

这次干脆不再继续调这些偏移量：**保留原主题的窄栏思路，只给文章页增加真正需要的目录空间。**

首页、搜索、标签、归档仍然使用原来的布局；正文也不因为屏幕变成 2K、4K 就无限变长。

## 文章布局：不用 transform 硬挪了

这次参考了 [VitePress](https://vitepress.dev/)、[Starlight](https://starlight.astro.build/) 和 [Fumadocs](https://fumadocs.dev/) 的目录布局。

不过我并不想把个人博客改成一个完整的文档站。左侧树形导航、复杂的布局框架，现在都用不上。

最后选了 CSS Grid。

文章页在宽屏下分成三个轨道：中间是约 720px 的阅读列，右边放目录，左边留出对应的空间，让正文保持视觉上的居中。屏幕宽度不足 1280px 时退回单栏。

这里有个比选 Grid 更重要的调整：**标题、日期、阅读时间、正文、标签、分享按钮和上一篇/下一篇，都放进同一条阅读轴。**

不再出现标题是一种居中方式，正文又是另一种居中方式的情况。

布局代码也收拢到了 `site-layout.css` 和 `PostContentLayout.astro`。上游的 `Layout.astro`、`PostLayout.astro`、Header 等基础结构继续沿用。

这样以后想调整阅读宽度，不必再去文章路由里翻一堆布局偏移值。

## 文章目录：桌面和手机不能完全用同一种交互

目录是这次最折腾的部分。

最早的需求很简单：把 Markdown 的 H2 列出来。但后来发现，**目录能显示**和**目录好用**完全是两回事。

### 桌面端：知道读到哪了就好

桌面端还是右侧的轻量目录，没有套厚重的卡片背景。

它会跟随阅读位置高亮当前章节；文章很长时，目录区域可以自己滚动；页面滚动时，目录借助 Sticky 保持在旁边。

H2、H3 标题直接来自 Astro 的 `render(post).headings`，不需要再引入一套 TOC 依赖。

活动章节的更新也只是原生滚动监听，配合 `requestAnimationFrame` 做节流。没什么花哨的技术，对这个博客已经够用了。

### 手机端：目录得随时找得到

在手机上，把折叠目录放在文章开头确实容易实现，原生 `details` 就能做。

问题是读到一半想跳章节时，得先滚回文章前面找它。

所以后来换成了右下角的固定目录入口，点开后是原生 `dialog`。选中章节就关闭，Esc 也能退出，并处理了基本的焦点返回。

但这里又踩了个坑。

AstroPaper 原本就有返回顶部按钮，而且手机上也是右下角。新加的目录按钮一开始只能往上躲。

最初想着给目录多加一点底部偏移，结果一个宽度正常，换个窄屏宽度又可能挤在一起。

仔细想想，这不就是之前用 `transform` 修正文位置的老路吗？

最后干脆让两个按钮各待一边：返回顶部在左下角，目录在右下角。

而且这条规则只写在文章页的响应式样式里，没有直接修改上游的 `BackToTopButton.astro`。

比继续维护几个神秘的 `bottom` 数值省心多了。

## 改了主题，以后怎么升级？

这次还有个一直在意的问题：上游兼容。

AstroPaper 更像一个可以直接改源码的项目模板，不是那种安装完主题包、只改配置文件就能完成所有定制的系统。

想重新组织文章页面，总归需要改一部分源码。

所以我现在不太会把“低侵入”理解为一个原文件都不动。

更现实的标准是：**改了什么、为什么改、下一次跟上游同步时怎么处理，都能说清楚。**

这次把布局和 TOC 尽量做成独立组件，CSS 则集中到 `site-layout.css`。原来的 `app-layout` 没改，不把其他页面一股脑拉宽。

真正绕不开的还是 `src/pages/posts/[...slug]/index.astro`。

它要负责加载文章、传递标题与 SEO 信息，还要把各个文章组件组织起来。想让标题、正文和目录共用正确的结构，就必须修改这个入口。

这是之后升级 AstroPaper 时最值得认真对照的地方。不能直接把上游新版文章路由整文件盖过来。

另一个有改动的上游文件是 `Footer.astro`。我想把 Astro、AstroPaper 和 Cloudflare Pages 的链接跟版权放在一起，所以做了很小的调整。

这种修改确实存在合并冲突的可能，但毕竟只有几条文字链接。为了避免这么一点改动，专门设计一套复杂的 Footer 扩展机制，感觉也没必要。

首页也多了一句小字：“虽然也没有什么技术含量。”

这纯粹是个人偏好，倒不是什么技术方案。

除此之外，原本已经能用的 SEO、OG、RSS、Pagefind、标签和 Markdown 渲染尽量都没有重新造一遍。

**低侵入不是不惜代价地绕开所有上游代码，而是让改动带来的好处，值得以后维护它的成本。**

## 上游其实也有人讨论过这个问题

查 AstroPaper 的 Issue 时，还看到一个挺巧的讨论：

[Issue #542：Improve or create a new toc component?](https://github.com/satnaing/astro-paper/issues/542)

提出的问题跟我遇到的很接近：长文章希望右侧有目录，还能看到自己读到哪个章节。

作者也参与了讨论，提到自己试过类似 `absolute + sticky` 的方案，以及页面出现两套目录、要不要默认集成这类功能等顾虑。

这让我觉得，上游不直接塞进一个完整侧栏，并不一定是忽略了需求。对一个走简洁路线的博客主题来说，多一个默认组件，本身也有代价。

所以这次没有另开重复 Issue。

等自己的方案再用一阵，如果有更有价值的实践反馈，再考虑回到那条讨论里交流。至于我的中文首页文案、Footer 署名和正文宽度，就没必要要求主题作者跟着我的偏好改了。

## 两个 PR，最后总算收住了

这段折腾主要分成两轮。

[PR #19](https://github.com/wingsky-1/my-blog/pull/19) 加了目录的初始实现、字数和阅读时长、分享按钮，以及第一版的文章布局。

[PR #20](https://github.com/wingsky-1/my-blog/pull/20) 则是给前一轮收拾布局问题：统一文章阅读轴，重新处理宽屏目录和移动端入口，还顺便整理了首页文案、页尾署名和升级文档。

两轮都没有额外引入 UI 框架、数据库或者服务端组件。静态构建、Pagefind 和 Cloudflare Pages 部署方式照旧。

另外，仓库里也留了一份 `docs/ASTROPAPER_UPGRADE_REVIEW.zh-CN.md`，专门记录哪些地方改了上游、哪些已经拆成独立组件，以及以后升级主题该怎么处理。

代码最终通过了 CI 和安全检查，Cloudflare Pages Preview 构建成功，人工看过实际页面后才合并到 `main`。

这件事也让我重新认识了“构建通过”四个字的分量。

它能证明很多事情，但证明不了两个浮动按钮在某个屏幕宽度下是不是挤到了一起。

这个还真得自己点开看看。

## 最后

折腾完以后，博客其实没有变得多花哨。

首页还是那个首页，正文还是偏窄的阅读布局，只是宽屏下多了个顺手的目录，手机上想跳章节也方便了些。

我觉得这样就挺好。

这次最大的收获倒不是学会了什么复杂的响应式技巧，而是给已有项目加功能时，不能只盯着当前组件能不能显示出来，还得看看它放进整张页面里会不会打架。

开源模板帮我们省掉了从零搭建的时间。但开始定制以后，后续的维护成本也得自己接住。

能复用就复用，该拆开的逻辑拆开，实在要修改上游的地方也不用太纠结，只要知道为什么改、以后怎么升级就行。

本来搭这个博客是想记录 VPS、家庭组网、Docker 和 AI 工具的实践。

结果先连续写了两篇关于博客本身的文章。

希望下一篇终于能回到正题。

虽然这句话，上次好像也说过。
